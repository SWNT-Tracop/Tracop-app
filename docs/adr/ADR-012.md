# ADR-012: Offline sync idempotency and serialized server cursors

## Context

Offline clients may retry operations after a timeout or reconnect, and pull clients need a cursor that does not skip changes committed concurrently. The sync module records processed operations and a change log in PostgreSQL. Catalog changes include globally readable taxonomy, owner-scoped lots, and delete tombstones.

## Decision

- **Idempotency:** each operation is processed in a transaction and claimed with a transaction-scoped PostgreSQL advisory lock keyed by `opId`. The service canonicalizes the operation JSON (sorting object keys) and stores its SHA-256 digest. A repeat from the same user with the same digest returns the stored result; a different digest for the same `opId` is rejected as `op_id_reused`. A processed operation belonging to another user is rejected.
- **Lock ordering and commit:** acquire the per-`opId` advisory lock before checking `processed_operations`. For a change that needs a sequence, acquire the single transaction-scoped sequence advisory lock immediately before the `change_log` `INSERT ... RETURNING`. After the change has been recorded, insert its `processed_operations` row; both changes commit together through the unit of work. The sequence lock serializes allocation with insertion so pull cursors cannot advance past an uncommitted lower sequence.
- **Push and pull:** `POST /sync/push` returns per-operation status and version, but does not return `serverSeq`; clients discover sequence numbers and changes through `GET /sync/pull`. Pull uses a numeric server cursor (`server_seq`), not a client timestamp. Its horizon and ordered page are read in one query; when another page exists, the next cursor is the last returned sequence, otherwise it advances to the server horizon. Changes originating on the same device are included.
- **Visibility:** catalog categories and products are recorded with no owner and are visible across users; their payloads contain catalog data, not user PII. Lot change records carry the lot owner's user ID and are visible only to that owner. Lot tombstones retain that owner scope and are private. Deletion is limited to draft lots; deleting a lot marks its photos deleted and records a tombstone. Published lots are cancelled rather than deleted.
- **Current request limits:** push accepts 1–50 operations and its JSON body limit is 256 KiB. Pull accepts limits from 1 to 500, defaulting to 200. The API advertises 413 for oversized push requests. Sync endpoints require authentication and are rate-limited.
- **Out of scope / known gaps:** retention or compaction of `change_log` and `processed_operations` is not implemented. Public catalog offline sync, photo synchronization, and a periodic sync worker are also outside the current implementation.

## Consequences

- Replaying an operation is safe within the retained processed-operation records, and reuse of an ID with different content is detected.
- The per-operation lock prevents concurrent duplicate execution; the global sequence lock provides ordered cursor semantics but serializes change-log inserts and can limit write throughput.
- Clients need a follow-up pull to learn the server sequence and receive canonical changes, including their own changes.
- Without retention, the change log and processed-operation table continue to grow; introducing cleanup requires a separate policy and must preserve idempotency and cursor guarantees.
- The body and operation-count limits constrain push batch size. Their values are implementation limits, not an assertion that all batches will fit the body limit.

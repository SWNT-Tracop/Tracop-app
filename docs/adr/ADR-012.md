# ADR-012: Idempotencia de sincronización offline y cursores de servidor serializados

## Contexto

Los clientes offline pueden reintentar operaciones después de un tiempo de espera agotado o al reconectarse, y los clientes que hacen pull necesitan un cursor que no omita cambios confirmados concurrentemente. El módulo `sync` registra las operaciones procesadas y un registro de cambios en PostgreSQL. Los cambios del catálogo incluyen una taxonomía legible globalmente, lotes restringidos por propietario y marcas de borrado (_tombstones_).

## Decisión

- **Idempotencia:** cada operación se procesa en una transacción y se reclama mediante un _advisory lock_ de PostgreSQL con alcance de transacción, cuya clave es `opId`. El servicio canonicaliza el JSON de la operación (ordena las claves de los objetos) y almacena su digest SHA-256. Si el mismo usuario repite la operación con el mismo digest, se devuelve el resultado almacenado; si usa el mismo `opId` con un digest diferente, se rechaza como `op_id_reused`. También se rechaza una operación procesada que pertenezca a otro usuario.
- **Orden de los locks y confirmación:** se adquiere el _advisory lock_ por `opId` antes de consultar `processed_operations`. Para un cambio que requiere una secuencia, se adquiere el único _advisory lock_ de secuencia con alcance de transacción inmediatamente antes del `INSERT ... RETURNING` en `change_log`. Una vez registrado el cambio, se inserta su fila en `processed_operations`; ambas modificaciones se confirman juntas mediante la unidad de trabajo. El lock de secuencia serializa la asignación con la inserción, de modo que los cursores de pull no puedan avanzar más allá de una secuencia menor aún no confirmada.
- **Push y pull:** `POST /sync/push` devuelve el estado y la versión de cada operación, pero no devuelve `serverSeq`; los clientes obtienen los números de secuencia y los cambios mediante `GET /sync/pull`. Pull usa un cursor numérico del servidor (`server_seq`), no una marca de tiempo del cliente. El horizonte y la página ordenada se leen en una sola consulta; si existe otra página, el cursor siguiente es la última secuencia devuelta; de lo contrario, avanza hasta el horizonte del servidor. Se incluyen los cambios originados en el mismo dispositivo.
- **Visibilidad:** las categorías y los productos del catálogo se registran sin propietario y son visibles para todos los usuarios; sus payloads contienen datos del catálogo, no PII de usuarios. Los registros de cambios de lotes incluyen el ID del usuario propietario y solo son visibles para ese propietario. Las marcas de borrado de lotes conservan ese alcance de propietario y son privadas. Solo se pueden borrar lotes en borrador; al borrar un lote, se marcan sus fotos como eliminadas y se registra una marca de borrado. Los lotes publicados se cancelan en vez de borrarse.
- **Límites actuales de las solicitudes:** push acepta de 1 a 50 operaciones y el límite del cuerpo JSON es de 256 KiB. Pull acepta límites de 1 a 500, con valor predeterminado de 200. La API anuncia el código 413 para solicitudes push que excedan el tamaño permitido. Los endpoints de sync requieren autenticación y tienen límites de frecuencia.
- **Fuera de alcance / brechas conocidas:** no está implementada la retención ni la compactación de `change_log` y `processed_operations`. La sincronización offline del catálogo público, la sincronización de fotos y un worker periódico de sync también están fuera de la implementación actual.

## Consecuencias

- Repetir una operación es seguro mientras se conserven sus registros en `processed_operations`, y se detecta la reutilización de un ID con contenido diferente.
- El lock por operación evita la ejecución concurrente de duplicados; el lock global de secuencia ofrece semántica de cursor ordenado, pero serializa las inserciones en el registro de cambios y puede limitar el rendimiento de escritura.
- Los clientes necesitan hacer un pull posterior para conocer la secuencia del servidor y recibir los cambios canonicales, incluidos los propios.
- Sin retención, el registro de cambios y la tabla de operaciones procesadas siguen creciendo; implementar una limpieza requiere una política aparte y debe preservar las garantías de idempotencia y de cursores.
- Los límites del cuerpo y de la cantidad de operaciones restringen el tamaño del lote push. Son límites de implementación; no implican que todos los lotes quepan dentro del límite del cuerpo.

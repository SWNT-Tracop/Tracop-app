# ADR-011: Lot Photos

## Contexto

Providers need to attach photos to lots without sending large files through the API. The flow must validate and normalize images before they appear in reads, restrict uploads, and allow orphaned objects to be recovered. The current implementation integrates S3-compatible storage and processes images in the API.

## Decisión

- `catalog` coordinates photos through `StoragePort` and `PhotoProcessorPort`. The API creates a reservation and a single-object S3 presigned POST policy under `incoming/`; the browser/app uploads directly to storage using the returned `url` and `fields`. The key contains 32 random bytes encoded as base64url.
- Storage uses `S3_API_*` credentials for API operations and `S3_POLICY_*` credentials to sign POST policies; when policy credentials are absent, the adapter reuses API credentials. The policy limits the upload to the configured maximum size. Processed keys are also random and stored under `photos/` with the `.webp` extension.
- On confirmation, the API checks object existence, size, and JPEG/PNG/WebP format; processes one image, applies orientation, converts to sRGB, limits dimensions, and always encodes the output as WebP. A photo moves through `pending`, `processing` (with a lease token and expiry), and `ready`. The lease prevents concurrent confirmations from completing the same reservation; after it expires, a later confirmation can claim it.
- Only `ready` photos are read. Reads return a presigned download URL, ID, and position; they do not expose independent `mediaRef` or `objectKey` fields. By protocol, the random processed-object key is present inside that URL, and the temporary key appears in the upload policy's `fields.key`.
- The manual purge expires pending reservations and deletes old, unreferenced objects under `incoming/` and `photos/` after the grace period. Automatic bucket cleanup is neither configured nor assumed.
- Input size/dimensions, output size, maximum photo count, reservation/URL expiries, purge grace, WebP quality, concurrency, lease, and rate limits are configurable through `CATALOG_PHOTO_*` variables. Current defaults: 5 photos; 5 MiB; 25,000,000 pixels; 10,000 input dimension; 2,048 output dimension; 1,800 s reservation; 900 s upload URL; 300 s download URL; 3,600 s purge grace; WebP quality 80; concurrency 2; 300 s lease; 30 preparations per user per 60 s. The configured maximum is capped at 5 photos and 5 MiB.
- `sharp` is added as the image processor (using libvips), together with the S3-compatible SDK for POST policies, object operations, and presigned URLs. The libvips license is an **open team decision**.

## Consecuencias

- Files upload directly to storage, and only the validated WebP version becomes visible; the API controls authorization, size, transformation, and temporary read access.
- The contract necessarily exposes random keys through protocol URLs/fields; clients must treat presigned URLs as temporary credentials and must not log them.
- Orphan cleanup requires running `catalog:purge-orphan-photos` externally. This task does not replace a bucket lifecycle policy for `incoming/`; the need and configuration for such a policy remain open.
- Use of real S3 and sufficiency of the minimum IAM permissions listed in `.env.example` have not yet been verified against a real provider.
- Processing consumes API CPU and memory; concurrency is limited per process and is not coordinated across instances.
